# 초안: 새 호가창 연구 설계 (사전 등록 전 구조만)

작성: 2026-11-11 · 상태: 초안. 아래 값은 아직 등록된 것이 아니다.
이 문서는 날짜를 붙여 커밋하기 전까지 사전 등록이 아니다. 데이터를 보기 전에 확정해야 한다.

## 1. 왜 다시 하나
- 이전 연구(ML_ORDERBOOK_60M_20261029)는 2026-10-31에 INSUFFICIENT_DATA로 끝났다.
- 원인: 학습 구간 192시간 중 호가창이 있는 시간이 115시간(59.9%)이었고, 사전 등록 기준은 90% 이상이었다. 규칙 문제가 아니라 데이터 구멍이었다.
- 메타 학습기는 계속 `COLLECT_ORDERBOOK`을 권고한다. 현재 후보 18개 중 보류 검증 통과는 0개다.
- 지금은 호가창 수집이 301개 마켓에서 정상이다 (24시간 약 43만 줄, 실패 0).

## 2. 시작 조건 (모두 만족해야 시작)
1. /health의 `orderBookCoverage.meetsStudyBar === true` 이고 `ratio >= 0.9` (#3079 배포 후 읽을 수 있음)
2. `longestGapHours`가 기준 이하 (기준은 등록 때 고정, 후보: 6시간)
3. 데이터 보존 기간(14일) 안에서 학습 192시간 + 보류 구간이 모두 확보됨
4. 이전 연구의 규칙은 바꾸지 않는다 (같은 규칙으로 데이터만 새로 채워 다시 한다). 규칙을 바꾸면 새 이름과 새 날짜로 등록한다.

## 3. 사전 등록 때 확정할 항목 (지금은 빈칸)
| 항목 | 값 | 비고 |

## 4. 하지 않는 것
- 데이터가 비는 시간을 채우거나 만들어 넣지 않는다.
- 결과를 본 뒤 규칙, 임계값, 구간을 바꾸지 않는다.
- 통과해도 승급 증거가 아니다. 정식 Research 실험과 그림자 운용을 거쳐야 하고, 한도, 위험, 자본, 권한은 바뀌지 않는다.
- 서버 코드나 주문 흐름에 연결하지 않는다 (PAPER 연구만).

## 5. 실행과 결과 보고
- 서버의 기존 Research 서비스가 읽기 전용으로 돌리고, 결과 줄만 가져온다 (이전과 같은 방식).
- 시작 전에 커버율 확인 결과를 작업지시서에 기록한다.
- 기록물: 사전 등록 문서(날짜 포함), 작업지시서, 결과 handoff.

## 6. 먼저 필요한 일
1. #3079 병합과 서버 배포 → 커버율 값 읽기
2. 커버율 < 90%이면: 구멍이 생긴 시간대와 원인을 찾는다 (오늘 서버 정지 같은 사건이 구멍을 만들었는지 확인)
3. 커버율 >= 90%이면: 위 3번 항목을 확정해 날짜를 붙여 등록한다.

## 7. 알려진 위험
- 오늘 14:05 KST쯤 서버가 25분 멈췄다. 이 시간의 호가창은 비었을 수 있다 (정시 샘플 1~2개 손실). 커버율에 반영되는지 배포 후 확인한다.
- 배포 때 백업이 디스크를 몰아 서버를 멈추게 한다. 배포 중에는 수집이 끊겨 커버율이 떨어질 수 있다. 연구 시작 전 구간에는 배포를 피하거나 백업을 가볍게 하는 수정이 먼저다.
