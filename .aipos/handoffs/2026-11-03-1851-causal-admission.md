### Approved-design candidate

Reuse the existing Worker and `NUSA_EXECUTION_COORDINATOR` binding, but add a dedicated isolated route and a dedicated DO operation/storage record. The server, never the request body, computes a canonical source identity and a domain-separated object name such as `nusa-isolated-causal:v1:<sha256(canonical source tuple)>`. The tuple should bind immutable repository ID plus repository name, source workflow path, source SHA, source run ID and attempt, and the verified event/ref. Store the verified manifest/artifact digest as claim attributes, not as a way to mint a second claim for the same source identity.

After OIDC, GitHub run/job/artifact metadata, and Sigstore checks all pass, one SQLite-backed DO transaction performs `get(claim-record)` and conditional `put(CLAIMED_PERMANENTLY)` with no network I/O in the transaction. A duplicate or conflicting record is rejected. The isolated method must require transactional storage and fail closed if unavailable; it must not use the generic lease fallback, `maxAcquisitions`, TTL, release, expiry, takeover, or a delete path. Keep both the DO object name and storage key domain-separated from production execution records. The Worker must retain the claim and invoke the isolated deterministic CodingRunner internally only after the committed claim; do not return a reusable execution permit to the workflow. If commit outcome, response, or runner completion is uncertain, never reacquire. A crash after claim but before execution can lose the attempt permanently: this is at-most-once, not exactly-once.

The consumer OIDC policy should require the GitHub issuer, a dedicated audience, valid signature/JWKS and time claims, exact immutable repository ID/name, exact consumer `workflow_ref` on `refs/heads/main`, expected `workflow_run` event, and matching publisher run ID/attempt verified against GitHub's API. The OIDC run identity is the consumer; source run ID/attempt/SHA from the event are untrusted input and must be separately checked by the Worker against the exact GitHub run, workflow, ref, event, conclusion, job and signed artifact. The protected consumer workflow must be the only code selecting the source tuple; do not execute source-checkout scripts in the OIDC-bearing job. GitHub documents that `workflow_run` runs from the default-branch workflow and has access to write tokens/secrets, so the job must not check out or execute untrusted PR code. OIDC `id-token:write` should be job-scoped; it does not itself grant repository write permission. Prefer a dedicated audience and remove consumer `checks:write` if the claim is recorded only in DO. No OIDC or GitHub token may enter logs, artifacts, or claim records.

This reuses an existing service and binding, so no new service, binding, Durable Object class, or namespace migration is proposed. It does add Worker routing and DO code and therefore requires a reviewed Worker deployment; production deployment authorization remains separate and is not granted here. The existing Worker GitHub API credential must be confirmed to have only the required read scope through non-secret permission evidence. The endpoint needs bounded request size/time, strict rate/abuse controls, sanitized responses/logs, and no calls to production causal admission, `/coding/propose`, `/coding/publish`, repository write APIs, risk/readiness, orders, or transfers.

One durability boundary remains explicit: ordinary DO restarts preserve SQLite state, but an operator restoring storage to a point before a claim could erase the tombstone. The at-most-once contract must prohibit pre-claim rollback or require claim-ledger reconciliation before re-enabling this route after restore. Permanent per-source records also require owner acceptance of retention and storage cost.
